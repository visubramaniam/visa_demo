# NVMe/TCP End-to-End Setup: VSP One Block 28 + RHEL

Ansible automation for configuring NVMe over TCP connectivity between a Hitachi Vantara VSP One Block 28 storage system and a Red Hat Enterprise Linux (RHEL) host with 100Gbps network adapters, including NVMe native multipathing.

## Overview

This project automates the full NVMe/TCP setup in two phases:

**Phase 1 — Storage Configuration (VSP One Block 28)**
1. Create LDEVs (logical devices) for NVMe/TCP namespaces
2. Create an NVM Subsystem with storage ports, host NQN registration, and auto-generate the subsystem NQN
3. Add namespaces and namespace paths to the NVM Subsystem

**Phase 2 — RHEL Host Configuration**
4. Install nvme-cli, configure NIC interfaces with static IPs, and verify storage connectivity
5. Load nvme_tcp kernel module, discover NVMe targets, connect to all controllers, and enable nvmf-autoconnect
6. Configure NVMe native multipathing (kernel-level) with round-robin IO policy via udev rules

## Prerequisites

- Ansible 2.14+ (tested with Ansible core 2.20.3)
- Python 3.9+ (tested with Python 3.14.3)
- Hitachi Vantara VSP One Block Ansible Collection: `hitachivantara.vspone_block`
- SSH access to the RHEL host (for delegated tasks)
- Network connectivity between the RHEL host and VSP One Block 28 storage ports
- RHEL 8.x or 9.x with NVMe/TCP support (kernel 4.18+)
- nvme-cli package (installed automatically by Step 4 if missing)

## Configuration

### 1. Encrypt Vault Files

Encrypt the credential files before use:

```bash
ansible-vault encrypt ansible_vault_vars/ansible_vault_storage_var.yml
ansible-vault encrypt ansible_vault_vars/ansible_vault_rhel_var.yml
```

### 2. Update Storage Variables

Edit `playbooks/vars/storage_rhel_vars.yml`:

| Variable | Description | Default |
|----------|-------------|---------|
| `rhel_pool_id` | Storage pool for LDEV creation | `0` |
| `rhel_ldev_start_id` | Starting LDEV ID | `5888` |
| `rhel_ldev_count` | Number of LDEVs to create | `10` |
| `rhel_ldev_size` | Size of each LDEV | `10GB` |
| `rhel_ldev_name_prefix` | LDEV naming prefix | `rhel_nvme_tcp_ldev` |
| `rhel_nvm_subsystem_name` | NVM Subsystem name | `NVMeTCP_RHEL_VSPOneB28` |
| `rhel_nvm_subsystem_host_mode` | Host mode for Linux | `LINUX/IRIX` |
| `rhel_storage_ports` | NVMe/TCP storage ports | `["CL1-D", "CL2-D"]` |
| `rhel_storage_port1_ip` / `rhel_storage_port2_ip` | Storage port target IPs | `192.168.10.30` / `192.168.20.30` |
| `rhel_nvme_tcp_port` | NVMe/TCP port | `4420` |
| `rhel_nvme_discovery_port` | NVMe discovery port | `8009` |
| `rhel_host_nqn` | RHEL host NQN (get via `cat /etc/nvme/hostnqn`) | — |
| `rhel_host_nqn_nickname` | Friendly name for host NQN | `rhel_host_nqn` |

### 3. Update RHEL Host Variables

Edit `playbooks/vars/rhel_vars.yml`:

| Variable | Description | Default |
|----------|-------------|---------|
| `rhel_nic1` / `rhel_nic2` | 100Gbps NIC interface names | `ens97f1` / `ens99f1` |
| `rhel_nic1_ip` / `rhel_nic2_ip` | NIC static IPs (same subnet as storage ports) | `192.168.10.45` / `192.168.20.45` |
| `rhel_nic_prefix` | Subnet prefix length | `24` |

### 4. Update Vault Credentials

Edit `ansible_vault_vars/ansible_vault_storage_var.yml`:
- `storage_address` — REST API IP of the VSP One Block 28
- `vault_storage_username` / `vault_storage_secret` — Storage credentials

Edit `ansible_vault_vars/ansible_vault_rhel_var.yml`:
- `rhel_hostname` — RHEL host IP address
- `vault_rhel_username` / `vault_rhel_password` — RHEL root credentials

## Step Details

### Step 1 — Create LDEVs

Uses `hitachivantara.vspone_block.vsp.hv_ldev` to create LDEVs in a loop. Checks existing LDEV state first and only creates LDEVs that do not already exist. Each LDEV is assigned a sequential ID starting from `rhel_ldev_start_id` (5888) and named with the pattern `rhel_nvme_tcp_ldev_XXXX`. LDEVs are created with compression and deduplication enabled.

### Step 2 — Create NVM Subsystem + Auto-Generate NQN

Uses `hitachivantara.vspone_block.vsp.hv_nvm_subsystems` to create a subsystem with:
- Two NVMe/TCP storage ports (`CL1-D`, `CL2-D`)
- Host mode set to `LINUX/IRIX`
- Namespace security enabled
- RHEL host NQN registered with nickname

After creation, the playbook **automatically constructs the subsystem NQN** from the creation result using the Hitachi NQN naming convention:

```
nqn.1994-04.jp.co.hitachi:nvme:storage-subsystem-sn.<serial[0]>-<serial[1:]>-nvmssid.<5-digit-id>
```

The constructed NQN is saved to `playbooks/vars/generated_rhel_nvm_nqn.yml` and automatically consumed by Step 5 — **no manual NQN entry required**.

### Step 3 — Add Namespaces and Paths

Adds each LDEV as a namespace to the NVM Subsystem using `state: add_namespace`. Each namespace is assigned a nickname (`rhel_nvme_tcp_ldev_ns_XXXX`) and mapped with the host NQN as the access path.

### Step 4 — Configure RHEL Networking and Install nvme-cli

Configures the RHEL host for NVMe/TCP connectivity:

1. **nvme-cli** — Installs the `nvme-cli` package if not already present
2. **Host NQN** — Reads and displays the host NQN from `/etc/nvme/hostnqn`
3. **NIC configuration** — Configures static IPs on both 100G NICs via `nmcli`
4. **Connectivity check** — Pings both storage port IPs to verify network reachability

> **Note:** All RHEL tasks use `delegate_to: {{ rhel_hostname }}` with SSH credentials from the vault.

### Step 5 — NVMe/TCP Target Discovery and Connect

Discovers and connects to the VSP One Block 28 storage:

1. **Kernel module** — Loads the `nvme_tcp` kernel module via `modprobe`
2. **Discovery** — Runs `nvme discover` against both storage port IPs
3. **Configuration** — Writes `/etc/nvme/discovery.conf` with both target entries and `ctrl-loss-tmo=-1` for infinite reconnect on path failure
4. **Connect** — Runs `nvme connect-all` to connect to all discovered controllers
5. **Autoconnect** — Enables and starts the `nvmf-autoconnect` systemd service for persistent connections across reboots
6. **Verification** — Lists connected namespaces (`nvme list`) and subsystem paths (`nvme list-subsys`)

### Step 6 — Configure NVMe Native Multipathing

Configures kernel-level NVMe native multipathing (not DM multipath):

1. **Status check** — Reads `/sys/module/nvme_core/parameters/multipath`
2. **Enable multipath** — Sets `nvme_core.multipath=Y` via `grubby` (if not already enabled)
3. **Disable DM multipath** — Stops and disables `multipathd`, removes `/etc/multipath.conf`, flushes DM multipath maps
4. **Udev rule** — Creates `/lib/udev/rules.d/71-nvme-iopolicy-hitachi-SVOS.rules` for automatic round-robin IO policy on Hitachi SVOS NVMe subsystems
5. **Initramfs** — Regenerates initramfs via `dracut -f -v` (if multipath was just enabled)
6. **Reboot notice** — Notifies that a reboot is required to activate multipathing

> **Important:** NVMe native multipathing operates at the kernel level and is the recommended approach
> for RHEL hosts. DM multipath (multipathd) is explicitly disabled since it is not compatible with
> NVMe native multipathing.

## RHEL Command Reference

Key commands used by the playbook:

| Command | Purpose |
|---------|---------|
| `modprobe nvme_tcp` | Load NVMe/TCP kernel module |
| `nvme discover --transport=tcp --traddr=<ip> --trsvcid=8009` | Discover NVMe targets |
| `nvme connect-all` | Connect to all discovered controllers |
| `nvme list` | List connected NVMe namespaces |
| `nvme list-subsys` | List NVMe subsystem paths (multipath view) |
| `cat /etc/nvme/hostnqn` | Read host NQN |
| `cat /sys/module/nvme_core/parameters/multipath` | Check native multipath status |
| `grubby --args=nvme_core.multipath=Y --update-kernel /boot/vmlinuz-$(uname -r)` | Enable native multipath |
| `dracut -f -v` | Regenerate initramfs |
| `cat /sys/class/nvme-subsystem/nvme-subsys*/iopolicy` | Verify IO policy |
