# NVMe/TCP End-to-End Setup: VSP One Block 28 + VMware ESXi

Ansible automation for configuring NVMe over TCP connectivity between a Hitachi Vantara VSP One Block 28 storage system and a VMware ESXi host with 100Gbps network adapters.

## Overview

This project automates the full NVMe/TCP setup in two phases:

**Phase 1 — Storage Configuration (VSP One Block 28)**
1. Create LDEVs (logical devices) for NVMe/TCP namespaces
2. Create an NVM Subsystem with storage ports, host NQN registration, and auto-generate the subsystem NQN
3. Add namespaces and namespace paths to the NVM Subsystem

**Phase 2 — ESXi Host Configuration**
4. Configure vSwitches, portgroups, and VMkernel adapters for 100Gbps NICs
5. Add the software NVMe over TCP adapter on both 100G NICs
6. Add NVMe/TCP target controllers for multipath connectivity

## Prerequisites

- Ansible 2.14+ (tested with Ansible core 2.20.3)
- Python 3.9+ (tested with Python 3.14.3)
- PyVmomi (for VMware modules): `pip install PyVmomi`
- Hitachi Vantara VSP One Block Ansible Collection: `hitachivantara.vspone_block`
- VMware Community Collection: `community.vmware`
- SSH access to the ESXi host (for `esxcli` commands via `ansible.builtin.raw`)
- Network connectivity between the ESXi host and VSP One Block 28 storage ports
- ESXi 7.0 U3+ or 8.0+ with NVMe/TCP support

## Configuration

### 1. Encrypt Vault Files

Encrypt the credential files before use:

```bash
ansible-vault encrypt ansible_vault_vars/ansible_vault_storage_var.yml
ansible-vault encrypt ansible_vault_vars/ansible_vault_esxi_var.yml
```

### 2. Update Storage Variables

Edit `playbooks/vars/storage_vars.yml`:

| Variable | Description | Default |
|----------|-------------|---------|
| `pool_id` | Storage pool for LDEV creation | `0` |
| `ldev_start_id` | Starting LDEV ID | `5888` |
| `ldev_count` | Number of LDEVs to create | `10` |
| `ldev_size` | Size of each LDEV | `10GB` |
| `ldev_name_prefix` | LDEV naming prefix | `nvme_tcp_ldev` |
| `nvm_subsystem_name` | NVM Subsystem name | `NVMeTCP_VSPOneB28` |
| `nvm_subsystem_host_mode` | Host mode for VMware | `VMWARE_EX` |
| `storage_ports` | NVMe/TCP storage ports | `["CL1-D", "CL2-D"]` |
| `host_nqn` | ESXi host NQN (get via `esxcli nvme info get`) | — |
| `host_nqn_nickname` | Friendly name for host NQN | `esxi_host_nqn` |

### 3. Update ESXi Variables

Edit `playbooks/vars/esxi_vars.yml`:

| Variable | Description | Default |
|----------|-------------|---------|
| `vmnic_100g_1` / `vmnic_100g_2` | 100Gbps NIC names | `vmnic2` / `vmnic3` |
| `vswitch1_name` / `vswitch2_name` | vSwitch names | `vSwitch_NVMe_TCP_1` / `vSwitch_NVMe_TCP_2` |
| `vswitch_mtu` | MTU (jumbo frames) | `9000` |
| `vmk1_portgroup` / `vmk2_portgroup` | Portgroup names | `NVMe_TCP_PG1` / `NVMe_TCP_PG2` |
| `vmk1_ip` / `vmk2_ip` | VMkernel adapter IPs | `192.168.52.36` / `192.168.52.37` |
| `vmk1_subnet` / `vmk2_subnet` | VMkernel subnet masks | `255.255.252.0` |
| `storage_port1_ip` / `storage_port2_ip` | Storage port target IPs | `192.168.52.31` / `192.168.52.32` |
| `nvme_tcp_port` | NVMe/TCP port | `4420` |
| `subsystem_nqn` | Fallback subsystem NQN (auto-generated by step 2) | — |

> **Note:** The `subsystem_nqn` is automatically constructed by Playbook 02 and saved to
> `playbooks/vars/generated_nvm_nqn.yml`. Playbook 06 loads this file automatically. The value
> in `esxi_vars.yml` serves only as a fallback if the generated file does not exist.

### 4. Update Vault Credentials

Edit `ansible_vault_vars/ansible_vault_storage_var.yml`:
- `storage_address` — REST API IP of the VSP One Block 28
- `vault_storage_username` / `vault_storage_secret` — Storage credentials
- `secondary_storage_address` — Secondary storage REST API IP (if applicable)

Edit `ansible_vault_vars/ansible_vault_esxi_var.yml`:
- `esxi_hostname` — ESXi host IP address
- `vault_esxi_username` / `vault_esxi_password` — ESXi root credentials
- `vcenter_hostname` — vCenter FQDN (optional, for vCenter-managed operations)

## Playbook Details

### Playbook 1 — Create LDEVs

Uses `hitachivantara.vspone_block.vsp.hv_ldev` to create LDEVs in a loop. Checks existing LDEV state first via `hv_ldev_facts` and only creates LDEVs that do not already exist. Each LDEV is assigned a sequential ID starting from `ldev_start_id` (5888) and named with the pattern `nvme_tcp_ldev_XXXX`. LDEVs are created with compression and deduplication enabled.

### Playbook 2 — Create NVM Subsystem + Auto-Generate NQN

Uses `hitachivantara.vspone_block.vsp.hv_nvm_subsystems` to create a subsystem with:
- Two NVMe/TCP storage ports (`CL1-D`, `CL2-D`)
- Host mode set to `VMWARE_EX`
- Namespace security enabled
- ESXi host NQN registered with nickname

After creation, the playbook **automatically constructs the subsystem NQN** from the creation result using the Hitachi NQN naming convention:

```
nqn.1994-04.jp.co.hitachi:nvme:storage-subsystem-sn.<serial[0]>-<serial[1:]>-nvmssid.<5-digit-id>
```

For example, serial `840498` and subsystem ID `0` produces:
`nqn.1994-04.jp.co.hitachi:nvme:storage-subsystem-sn.8-40498-nvmssid.00000`

The constructed NQN is saved to `playbooks/vars/generated_nvm_nqn.yml` and automatically consumed by Playbook 06 — **no manual NQN entry required**.

### Playbook 3 — Add Namespaces and Paths

Adds each LDEV as a namespace to the NVM Subsystem using `state: add_namespace`. Each namespace is assigned a nickname (`nvme_tcp_ldev_ns_XXXX`) and mapped with the host NQN as the access path.

### Playbook 4 — Configure ESXi Networking

Configures the ESXi network stack for NVMe/TCP in the correct dependency order:

1. **vSwitches** — Creates one vSwitch per 100G NIC (`community.vmware.vmware_vswitch`) with MTU 9000
2. **Portgroups** — Creates a portgroup on each vSwitch (`community.vmware.vmware_portgroup`)
3. **VMkernel adapters** — Creates VMkernel NICs with static IPs (`community.vmware.vmware_vmkernel`)
4. **NVMe/TCP tagging** — Tags VMkernel interfaces for NVMe/TCP traffic via `esxcli network ip interface tag add` (SSH)

> **Note:** VMware modules require PyVmomi and connect to the ESXi API on port 443.
> The tagging tasks use `ansible.builtin.raw` with SSH delegation since ESXi does not have Python.

### Playbook 5 — Add NVMe/TCP Adapter

Enables the software NVMe over TCP adapter on **both** 100G NICs via:

```bash
esxcli nvme fabrics enable --protocol TCP --device <vmnic>
```

Runs once per NIC (`vmnic2`, `vmnic3`) and verifies with `esxcli nvme adapter list`. All commands execute over SSH using `ansible.builtin.raw` with `delegate_to`.

### Playbook 6 — Add NVMe/TCP Target Controllers

Connects ESXi to the VSP One Block 28 storage subsystem through two target controllers (one per storage port) for active-active multipath:

```bash
esxcli nvme fabrics connect --adapter <vmhba> --ip-address <storage_ip> --port-number 4420 --subsystem-nqn <nqn>
```

**Automatic NQN loading:** Loads the auto-generated NQN from `vars/generated_nvm_nqn.yml` (created by Playbook 02). Falls back to the `subsystem_nqn` value in `esxi_vars.yml` if the file does not exist.

**Idempotent:** Re-running the playbook when controllers are already connected succeeds gracefully — the "Controller already connected" response is handled via `failed_when` logic.

**Verification:** Lists connected controllers via `esxcli nvme controller list` and visible namespaces via `esxcli nvme namespace list`.

## ESXi Command Reference

The ESXi-side playbooks (04, 05, 06) use `ansible.builtin.raw` with SSH delegation because ESXi does not include a Python interpreter. Key `esxcli` commands used:

| Command | Purpose |
|---------|---------|
| `esxcli nvme fabrics enable --protocol TCP --device <vmnic>` | Enable NVMe/TCP adapter |
| `esxcli nvme adapter list` | List NVMe adapters |
| `esxcli nvme fabrics connect --adapter <vmhba> --ip-address <ip> --port-number <port> --subsystem-nqn <nqn>` | Connect to storage controller |
| `esxcli nvme controller list` | List connected NVMe controllers |
| `esxcli nvme namespace list` | List visible NVMe namespaces |
| `esxcli network ip interface tag add -i <vmk> -t NVMeTCP` | Tag VMkernel for NVMe/TCP |
